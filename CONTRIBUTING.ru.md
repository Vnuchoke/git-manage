# Руководство для участников проекта

Спасибо за интерес к проекту! Сначала ознакомьтесь с [README на русском языке](README.ru.md), где описаны назначение проекта, его возможности и планы развития. Вы можете обсуждать идеи и сообщать о проблемах через Issues, а также предлагать изменения с помощью Pull Request (PR).

## Среда разработки

- Node.js версии 22 или новее
- pnpm 9 (версия закреплена в поле `packageManager` корневого файла `package.json`; рекомендуется выполнить `corepack enable`, чтобы Node.js управлял версией pnpm автоматически)

Подготовка окружения:

```bash
# Клонировать репозиторий
git clone https://github.com/GuoChen-thlg/git-manage.git
cd git-manage

# Установить зависимости (скрипт prepare автоматически включит Git-хуки через Husky)
pnpm install
```

## Основные команды

| Команда | Описание |
| --- | --- |
| `pnpm test` | Запустить Vitest в режиме наблюдения (watch mode) для непрерывного запуска тестов во время разработки |
| `pnpm exec vitest run --dir packages` | Однократно запустить все тесты (на момент написания исходного руководства — 667); рекомендуется перед отправкой изменений |
| `pnpm typecheck` | Выполнить полную проверку типов TypeScript для пакетов `core` и `openchamber` |
| `pnpm build` | Собрать три пакета; `core` и `openchamber` собираются отдельно |
| `pnpm lint` | Временно недоступна: ESLint ещё не настроен для использования flat config. Не полагайтесь на эту команду до завершения настройки |

## Правила оформления коммитов

В репозитории используется стандарт [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). Формат сообщения коммита:

```text
<type>: <subject>
```

Допустимые значения `type`: `feat` (новая функциональность), `fix` (исправление ошибки), `docs` (документация), `chore` (вспомогательные изменения), `ci` (непрерывная интеграция), `refactor` (рефакторинг), `test` (тесты), `style` (оформление кода), `perf` (производительность), `build` (сборка), `revert` (отмена изменений).

**Важно**: согласно правилам исходного репозитория, поле `subject` должно кратко описывать изменение **на китайском языке**.

Реальные примеры коммитов из репозитория (сообщения сохранены без изменений, ниже приведён перевод):

- `feat: 删除分支去掉确认直接删并支持 IDEA 式还原通知` — удаление ветки без дополнительного подтверждения с возможностью восстановления через уведомление в стиле IDEA
- `fix: 修复删除分支不可用问题` — исправление ошибки, из-за которой не работало удаление ветки
- `docs: 新增规格覆盖盘点文档` — добавление документа с анализом покрытия спецификаций

При создании коммита автоматически выполняются два Git-хука:

- **pre-commit**: запускает полную проверку типов для обоих пакетов. При ошибках коммит блокируется
- **commit-msg**: проверяет формат сообщения через commitlint. Коммит с сообщением, не соответствующим Conventional Commits, блокируется

## Ветки и Pull Request

- Разрабатывайте изменения на основе ветки `dev`: создавайте от неё отдельную ветку для каждой задачи или функциональности
- Один PR должен решать одну конкретную проблему — это упрощает проверку изменений
- В описании PR указывайте причину изменений (какую проблему они решают) и способ решения (как именно она устранена)
- Все проверки CI должны пройти успешно: сборка, проверка типов и полный набор модульных тестов обязательны перед слиянием
- Изменения поведения (новые возможности или исправления ошибок) должны сопровождаться новыми тестами либо обновлением существующих

## Сообщения о проблемах и предложения

Используйте шаблоны Issues, доступные в репозитории:

- **Сообщение об ошибке (Bug Report)**: укажите понятные шаги для воспроизведения (последовательность действий, соответствующие ветки и состояние репозитория), а также сведения об окружении (ОС, версия OpenChamber, версия Git Manage)
- **Предложение функциональности (Feature Request)**: опишите сценарий использования и ожидаемое поведение. Если в IntelliJ IDEA есть аналогичный интерфейс, приложите описание его работы, чтобы упростить согласование деталей взаимодействия

## Краткий обзор архитектуры

Проект организован как pnpm workspace и содержит два основных пакета:

- **`packages/core`**: независимый от редакторов слой Git-функциональности на чистом TypeScript, пригодный для повторного использования. В перспективе он должен поддерживать OpenChamber, VSCode и другие платформы
- **`packages/openchamber`**: расширение OpenChamber из двух частей — `panel` (пользовательский интерфейс) и `service` (серверная часть, выполняющая Git-команды). Использует Git-функциональность пакета `core`

В качестве ориентиров для внесения изменений можно использовать следующие спецификации:

- [docs/git-ide-feature-spec.md](docs/git-ide-feature-spec.md) — спецификация возможностей окна Git в IntelliJ IDEA
- [docs/spec-coverage.md](docs/spec-coverage.md) — анализ реализованного покрытия спецификаций; непокрытые пункты могут стать задачами для новых участников
